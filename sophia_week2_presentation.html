Where we were last week

Why LiveKit, the architecture pitch

Last week we presented the case for using LiveKit as our voice-agent orchestrator in production — bringing our existing AWS-hosted models (Whisper, Qwen3-VL, Kokoro, sophia-spatial-ai) into LiveKit's framework so we don't have to rebuild the orchestration plumbing ourselves.

01 What LiveKit gives us free
VAD, turn detection, interruption handling, preemptive generation, transcription syncing, browser-native AEC, full WebRTC stack (SFU + ICE + Opus). Plus 69 model plugins.
02 Our plug-in model
Bring our own STT / LLM / TTS / RAG. Route their endpoints through LiveKit's openai plugin. Zero custom plugin code for the happy path.
03 The end-state vision
One stack on a Mac driving four user experiences: Safari demo, Unity Mac Editor, Beam Pro Android app, XREAL glasses on Beam Pro.

Target 1 of 4

Browser application

Full OSS LiveKit + AWS models, served to Safari via agent-starter-react

What's running

  • livekit-server on the Mac at port 7880 (Apache 2.0 OSS, brew-installed)
  • token_mint FastAPI issuing JWTs at port 8001
  • agent worker running our Python agent.py with VAD + turn detection prewarmed
  • pf-gpu.sh port-forwarding to 4 model pods on AWS EKS
  • agent-starter-react Next.js frontend at port 3000

The voice loop

browser mic → WebRTC AEC → SFU → agent worker → Whisper STT (~1.6s) → sophia-spatial-ai /retrieve → Qwen3-VL LLM (streaming) → Kokoro TTS (per-sentence) → SFU → browser speakers

Three React overlays render live: state pill, event log with per-stage metrics, RAG sources side panel showing matched PDF pages.

Target 2 of 4

Unity on Mac (Editor)

Same backend, new client — built in Unity 6 with LiveKit Unity SDK

Why Unity (not native Kotlin)

  • Future 3D AR rendering. Unity + XREAL SDK 3.1.0 bakes stereo + head pose + camera + eventually XREAL Eye into one toolchain. Native Kotlin would force a rewrite for Phase 3.
  • Same C# code → Mac Editor + Android APK, no fork.
  • Phased build: Phase 1 voice-only first, AR overlays Phase 2, vision Phase 3.

What we wrote

SophiaConfig.cs
ScriptableObject holding all runtime config (SFU URL, token endpoint, room mode, identity). One asset, no recompile.
SophiaConnection.cs
MonoBehaviour: token fetch → Room.Connect → publish mic → subscribe Sophia's TTS audio track.
token_mint.py
Backend tweak: attach RoomConfiguration(agents=[RoomAgentDispatch(...)]) to JWT so non-web clients trigger agent dispatch.
sophia-scene.unity
One scene, one GameObject with SophiaConnection attached + SophiaConfig.asset wired.

Result: hit Play in Unity Editor → voice loop end-to-end through MacBook Pro speakers. Same agent, same models, same round-trip.

Target 3 of 4

Android APK on Beam Pro

The same Unity project, built as a native ARM64 Android app

From Editor to APK

  • Switched build target to Android (ARM64, IL2CPP)
  • Unity cross-compiled C# → IL → C++ → native ARM64 libil2cpp.so
  • Bundled Unity Android Player + LiveKit FFI Rust client (Android .so) + XREAL plugins + scenes + manifest
  • Output: sophia-glasses.apk
  • adb install -r from Mac, USB-tethered to Beam Pro

What we observed

  • Voice loop worked first try through Beam Pro's built-in mic + speaker
  • No sample-rate issues — Android audio is 48 kHz natively (unlike macOS)
  • No echo loop — validates that the macOS echo was geometry-specific, not Unity-fundamental
  • Same backend, same models, no code change between Mac Editor and Android

Bundle ID: com.UnityTechnologies.com.unity.template.urpblank (default template name — to be renamed com.sophia.glasses in Phase 2 cleanup).

Target 4 of 4

The full stack — XREAL One Pro on Beam Pro

Plug glasses in. Wear them. Talk. Beam Pro stays in pocket.

How it works

  • Zero APK changes. Same binary as Target 3.
  • Speakers: XREAL One Pro near-ear directional speakers — auto-routed by Android USB Audio Class.
  • Microphone: XREAL One Pro built-in dual-mic array — also auto-routed by Android.
  • Network: Beam Pro → Tailscale → Mac SFU at 100.69.34.194:7880. Glasses don't see the network at all.
  • Beam Pro placement: anywhere on your person within the ~1.2m tether reach. Pocket works.

The echo prediction held

On Mac Editor with built-in speakers + mic at ~20cm apart, we hit an acoustic feedback loop — Sophia echoing back into the mic (Unity has no AEC; LiveKit's Unity SDK doesn't wire playback into APM).

We predicted glasses geometry would kill it: near-ear directional speakers + mic on Beam Pro at arm's length = loop gain too low. Confirmed empirically — no echo on the glasses. No mic gating needed for Phase 1 ship.

Behind the scenes

Notable challenges we solved

The interesting problems
A Acoustic echo loop on Mac
Speakers → mic feedback on the Editor. Unity has no AEC; LiveKit's Unity SDK doesn't wire playback into APM. Predicted glasses geometry would kill it. Validated on hardware — no echo. Mic gating deferred indefinitely.
B Sample rate mismatch (44.1k vs 48k)
OnAudioFilterRead follows the macOS output device sample rate; EarPods are 44.1k-locked, RtcAudioSource expects 48k. Fix: use a 48k-capable output (MacBook speakers). Android isn't affected — VOICE source is always 48k.
C Token URL routing
token_mint returned ws://localhost:7880 — the Mac's view of localhost. On Beam Pro, that's the Beam Pro itself. Fix: client always uses its own configured URL; ignores server-side URL hint.
D Android permission race
Unity's RequestUserAuthorization returns immediately on Android — script gives up before user taps Allow. Path A shipped today: 20s poll-retry. Path B JNI bridge bundled with AEC fix for Phase 2.
E LiveKit SDK install gotchas
Git LFS pointer files instead of FFI binaries; Google.Protobuf runtime missing; NuGet menu hidden by Safe Mode. Documented as Q44 — comprehensive recovery procedure for any future install.
F Unity 6 + XREAL build constraints
minSdk 25 vs XREAL's 29 requirement; Unity 6 uses UnityPlayerGameActivity not UnityPlayerActivity; scene list defaults to empty SampleScene. All five gotchas catalogued as Q45 with checklist.

Multi-user · Concept

Two ways multiple people use Sophia

Same backend supports both. One config field decides which.
B Scenario B — Isolated rooms

Each user gets their own private room. Their own Sophia worker subprocess. Their own chat history. No overlap with anyone else.

Default in today's APK. 10 Beam Pros launch simultaneously = 10 isolated Sophia sessions.

Best for: single-tech troubleshooting, privacy-sensitive conversations, multi-tenant deployment

A Scenario A — Shared room

Multiple users join the SAME room. ONE Sophia serves all of them. Shared chat context — Sophia knows everyone's questions and answers.

First user triggers agent dispatch; subsequent users join the existing session. Per-room agent dispatch deduplication is built into LiveKit's SFU.

Best for: tech + remote expert pairing, supervisor-recorded inspections, training scenarios, multi-tech teardowns

Real-world use cases unlocked by Scenario A: Field tech wearing glasses + remote expert on browser, both in the same room, both ask Sophia questions, both see same answers and RAG sources. Training: senior wears glasses, trainee wears glasses, both observe the same conversation with their own AR overlays. Inspection: tech does walkthrough, supervisor on browser sees live transcript + sources, conversation auto-archives.

Multi-user · Production

Going from one Mac to many client companies

SaaS multi-tenant pattern: shared infrastructure, per-client isolation via hierarchical room naming

Tenant isolation in one line

Room name is hierarchical: {client_id}/{session_id} Examples: acme/maintenance-bay-3 # Acme team room acme/user-john-uuid # John's private globex/bay-2 # Globex team

Three enforcement layers prevent cross-tenant leakage:

  • JWT issuance: token_mint refuses tokens for rooms whose prefix doesn't match user's tenant
  • SFU validation: forged room names fail JWT signature check
  • Agent RAG scoping: worker parses room name → uses that client's RAG index only

Migration path from today's MacBook

Total lift: ~1-2 person-months of ops + auth + admin work.

The voice-agent code itself stays unchanged. The architectural pattern (LiveKit + JWT-encoded room names + per-room agent dispatch) was already production-correct from day one.

Multi-user · Just shipped

The picker UI

One APK, runtime choice between private and team modes

How the user experiences it

  • Launch app → picker screen shown (built at runtime, no Unity Editor wiring)
  • Tap "Start Private Session" → auto-generated unique room, isolated Sophia (Scenario B)
  • Tap "Join Team Session" → type a room code → joins shared room (Scenario A); if anyone's already there, same Sophia serves all
  • Tap "End Session" → mic disconnects, agent recycled, returns to picker
  • Tap "Quit App" → full app exit, returns to Android launcher
  • Cycle freely — pick → use → end → pick again, no app restart needed

What's running under the hood

SophiaSessionContext.cs
Static state holder for the user's session choice (mode + room override)
SessionPicker.cs
Builds Screen Space - Overlay Canvas + 4 buttons + input field at runtime; toggles SophiaConnection GameObject active/inactive
SophiaConnection.cs
Reads room from SessionContext first, falls back to config. New OnApplicationPause + OnApplicationQuit handlers so Android swipe-away disconnects cleanly
SophiaOverlayUI.cs
HUD canvas now builds in OnEnable, tears down in OnDisable — so the AR overlays rebuild fresh per session

~520 lines of new C# + ~45 lines of edits. Zero backend changes.

Why this matters: Until today, switching between private and team mode required rebuilding a different APK per deployment. Now one APK ships everywhere; the user decides at launch. This is the UX foundation for both single-tech enterprise rollout AND multi-tech team scenarios shipping in the same product.
