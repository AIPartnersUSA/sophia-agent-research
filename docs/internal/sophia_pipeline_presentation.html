The Problem

What we're building

  • Real-time conversational voice agent
  • End-user device: XREAL glasses tethered to Android phone
  • Pipeline: STT → RAG → TTS
  • Phone is the LiveKit client; glasses are display + optional mic/camera

Hard requirements

  • Open-source (no vendor lock for production)
  • Self-hostable on AWS
  • End-to-end first-audio-byte: ~600 ms
  • Real conversational UX (interrupts, turn-taking, no echo)
  • RAG-grounded answers (your AWS endpoint)
Two architectures considered: cascaded (STT → LLM → TTS) vs end-to-end STS (audio-LLM with RAG hooks)

"Models alone aren't enough."

A great STT + a great LLM + a great TTS does not equal a great voice agent.

The scenario we want to avoid:
"My RAG is working fine — answers are correct. But the user isn't enjoying the conversation."
Because the agent cuts them off mid-pause. Talks over them. Echoes its own voice. Waits 2 seconds before responding. Can't be interrupted. The retrieval is right; the conversation feels broken.

What's missing is the environment — the orchestration layer
that turns three models into a real conversation.

What "orchestration" actually means

Concrete examples of where a naive STT→LLM→TTS pipeline breaks:

ConcernProblem if missing
VAD (voice activity detection)Stream silence to STT 24/7 → wasted compute, hallucinated transcripts

Barge-in / interruptionAgent monologues over the user; no way to stop it mid-sentence

VAD vs Turn Handling — different problems

The two are constantly conflated. They solve completely different problems at completely different time scales.

QuestionAnswered byTime scaleType
"Is the user PHYSICALLY making sound RIGHT NOW?" VAD Per audio frame (~30 ms) Mechanical
"Is the user DONE EXPRESSING their thought?" Turn detector Per utterance (~seconds) Semantic

VAD = mechanical

VAD output is NOT raw per-frame decisions — it's a clean stream of SpeechStarted / SpeechEnded events with timestamps, computed by aggregating frame-level probabilities through hysteresis and duration filters.

Doesn't know what the user said. Doesn't know if a thought is complete. Doesn't know about conversation.

Models / implementations
Silero VAD (MIT) ← Sophia WebRTC VAD (BSD) ten-vad (Apache) Picovoice Cobra (proprietary)

Turn detection = semantic

Does this utterance feel complete? Reads the recent transcript, predicts probability the user is done.

Owns more than just end-of-turn: barge-in, endpointing timing, preemptive generation.

Models / implementations
LiveKit MultilingualModel (Apache) ← Sophia LiveKit English Turn Detector (Apache, EN-only, lighter) Pipecat smart-turn-v2 (BSD-3) STT-based endpointing (Deepgram, AssemblyAI) Pure VAD timeout (dumb fallback)
VAD gives temporal scaffolding (when sound starts/stops). Turn detection gives semantic scaffolding (when a thought is complete). Complementary, not redundant.

VAD — the per-frame primitive

Purpose: detect speech presence per frame, robustly. Everything else builds on this.

Without VAD: STT receives constant silence/noise (wasted compute, hallucinated transcripts) · No barge-in detection (can't detect user speaking while agent talks)· No "user started speaking" event · Agent either listens to everything or nothing.

Silero VAD args — each tunes "detect speech per frame, robustly"

ArgDefaultWhat it controls
activation_threshold0.5ENTER threshold: probability ≥ this → "speech" | Direct main-classifier knob. Higher = stricter.
deactivation_thresholdauto ≈ 0.35EXIT threshold: probability < this → "not speech" | Hysteresis — once in speech mode, lower bar to stay. Prevents flickering when intra-word energy briefly dips.
min_speech_duration0.05 sReject chunks shorter than this | Filters single-frame false positives (clicks, pops). Speech must be ≥50 ms.
min_silence_duration0.55 sRequired silence to declare speech ENDED | Smooths over normal between-word gaps. Without this, every micro-pause would fire SpeechEnded.
prefix_padding_duration0.5 sAudio kept BEFORE detected speech start | Captures word onset that the model itself might miss. STT gets the lead-in syllable.
max_buffered_speech60.0 sCap on single chunk length | Memory cap. Forces chunk boundary after 60 s for very long utterances.
sample_rate16000Audio rate for inference | Required by Silero model (trained on 16 kHz)
None of these args know about conversation, turns, or LLMs. They're all about making frame-level "is there speech?" decisions robust. VAD doesn't decide when a turn is over, doesn't know what the user said, doesn't know if a thought is complete.

Turn handling — silence ≠ turn end

Why turn handling is needed? To decide when USER'S UTTERANCE is complete enough to send to the LLM. VAD says "silence detected for 550 ms." But silence alone can't tell you if the user is done:

User saysSilence afterTurn complete?
"what's the weather today"600 ms✅ Yes — clear question
"I want to know about… uh…"800 ms❌ No — mid-thought hesitation
"Let me think…"1500 ms❌ No — thinking pause
"ok"400 ms✅ Yes — short but complete

A pure silence-timeout can't distinguish these. Set timeout low → cut off mid-sentence. Set high → painful waits. That's why semantic turn detection (`MultilingualModel`) exists. Reads recent transcript, predicts probability user is done. "I want to know about" with a pause → P(done) low. "what's the weather today" with a pause → P(done) high.

Plus turn handling owns more than just end-of-turn detection — it handles **barge-in** (user speaks while agent talks), **endpointing** (timing rule), and **preemptive generation** (speculative LLM call)

Four sub-blocks of turn_handling

turn_detection — WHICH signal decides "user done"

ValueContribution
"vad"Use only silence timeout. Cheap, dumb. Cuts off pauses.
"stt"Use STT's own endpointing signal. Variable quality across providers.
MultilingualModel()Semantic — reads transcript history, predicts P(end). Smartest. Sophia's current setting.
"realtime_llm"Realtime API (OpenAI/Gemini Live) emits server-side turn events.
"manual"You drive turns programmatically.

endpointing — WHEN to declare turn over (timing rules even with a semantic detector)

ArgDefaultContribution
mode"fixed"Constant timeout ("fixed") vs adaptive ("dynamic").
min_delay0.5 sFloor — even if detector is sure, wait at least this long. Prevents over-eagerness.
max_delay3.0 sCeiling — force turn-end after this long. Prevents infinite waits.
alpha0.9EMA history weight for "dynamic" mode.

interruption — barge-in (different from end-of-turn)

Turn-end = user finished, agent now talks. Barge-in = agent is talking, user speaks anyway.

ArgDefaultContribution
enabledTrueMaster switch — set False = agent always finishes.
modeauto"adaptive" (ML-based) vs "vad" (raw VAD trigger).
min_duration0.5 sFilters coughs / clicks — must speak ≥500 ms to count as interrupt.
min_words0Min word count to count as interrupt (STT-mode only).
discard_audio_if_uninterruptibleTrueWhen uninterruptible, drop buffered audio (don't queue interruption for later).
resume_false_interruptionTrueBrief interrupt → agent resumes original utterance from where it stopped.
false_interruption_timeout2.0 sAfter this silence post-interrupt → reclassify as false.
backchannel_boundary(1.0, 3.5)Suppress interruption at (start, end) of agent's turn. Handles "mm-hmm" backchannels and STT timestamp drift. End value higher than start because STT timestamps aren't very reliable.

preemptive_generation — speculative LLM call

While turn detector is still computing, start LLM in parallel. Save latency.

ArgDefaultContribution
enabledTrueStart LLM speculatively when detector leans toward "end".
preemptive_ttsFalseAlso start TTS speculatively. Riskier — wastes TTS compute on cancelled turns.
max_speech_duration10.0 sSkip preemption for utterances longer than this — long utterances more likely to change.
max_retries3Cap on speculative-call retries per turn (resets when turn completes).

MultilingualModel() args (the model itself)

ArgDefaultContribution
unlikely_thresholdNone (per-language defaults)Override "unlikely end-of-turn" threshold. Lower = more eager to end.
MAX_HISTORY_TURNS (internal)6Only the last 6 turns sent for prediction. Not user-tunable.

Lifecycle — VAD + turn handling in cooperation

User starts speaking
  ↓
[VAD] activation_threshold crossed for >min_speech_duration → SpeechStarted
  ↓
[STT] streams audio, emits interim transcripts
[Turn detector] reads interims, computes P(end) continuously
  ↓
User pauses
  ↓
[VAD] silence >min_silence_duration → SpeechEnded   (just means "no more sound")
  ↓
[Endpointing] starts countdown (must wait min_delay before turn ends)
[Turn detector] given final transcript, predicts P(end)
  ↓
Decision branch:
  IF P(end) > threshold AND endpointing min_delay elapsed:
    → Turn confirmed, send to LLM (or use preemptive result)
    → TTS speaks response
  IF P(end) low AND max_delay not elapsed:
    → Wait. User probably paused mid-thought.
  IF max_delay elapsed regardless:
    → Force turn end

While agent speaking:
  [VAD] runs continuously
  IF user speech > min_interruption_duration AND not in backchannel_boundary:
    → Barge-in! Cancel TTS, cancel LLM, return to listening
  IF brief speech then silence > false_interruption_timeout:
    → Resume agent's original utterance from where it stopped
ApproachProsCons
VAD alone (turn_detection="vad")Cheap, no extra modelCuts off mid-sentence pauses, can't distinguish hesitation
Turn detector aloneSemantic, accurateNeeds VAD silence events as trigger
STT-based (turn_detection="stt")Free (STT engine usually has endpointing)Variable quality; not as smart as semantic
VAD + MultilingualModel (Sophia's current)Best — VAD handles fast per-frame events; turn detector handles slow semantic completenessMore compute (extra ONNX); more args to tune

other concerns

AEC echo handling

What it is: Cancel the agent's own voice before it gets re-fed into STT (otherwise infinite loop -- agent transcribes itself).

Who handles it:

  • WebRTC AEC -- runs client-side in the browser / Android SDK. Standard WebRTC primitive, automatic.
  • LiveKit framework -- adds aec_warmup_duration=3.0 s (AgentSession arg). Tells the agent "ignore user audio for the first 3 s of agent speech" so AEC has time to converge before barge-in detection trusts the mic.

Where: WebRTC stack (transport layer) + voice/agent_session.py (warmup timer)

State machine

What it is: Tracks "what is the agent doing right now?" so audio + LLM + TTS don't race. States: listening -> thinking -> speaking -> interrupted.

Who handles it:

  • AgentActivity class (voice/agent_activity.py) -- the per-session state machine. Owns the lifecycle of one user turn.
  • AgentSession -- holds agent_state and user_state properties; emits agent_state_changed events you can subscribe to.
  • SpeechHandle scheduler -- per-utterance state (queued / playing / cancelled / done).

Where: voice/agent_activity.py, voice/agent_session.py, voice/speech_handle.py

Streaming hand-off (STT -> LLM -> TTS)

What it is: Pipe STT transcript chunks into the LLM, pipe LLM token chunks into TTS, all while preserving sentence boundaries so TTS can start speaking the first sentence before the LLM finishes.

Who handles it:

  • generate_reply() in voice/generation.py -- consumes the LLM's ChatChunk stream, splits text deltas (-> TTS) from tool-call deltas (-> @function_tool execution).
  • StreamAdapter -- wraps non-streaming STT/TTS plugins so the rest of the pipeline can pretend everything streams.
  • Sentence tokenizer (blingfire) -- splits LLM text into sentences for TTS engines that synthesize per-sentence.
  • transcription_node -- runs between LLM and TTS; strips markdown / emoji / does pronunciation fixes.

Where: voice/generation.py, stt/stream_adapter.py, tts/stream_adapter.py, voice/agent.py (transcription_node hook)

Audio I/O orchestration

What it is: Move raw audio frames between mic / SFU / STT / TTS / speaker while normalizing sample rates, codecs, and chunk boundaries.

Who handles it:

  • livekit-rtc (Python bindings to the Rust SDK) -- raw WebRTC frame I/O, codec negotiation (Opus on the wire), packet jitter buffer.
  • AgentSession.input / .output -- typed channels for audio / video / text. Routes mic frames to STT and TTS frames to SFU.
  • Framework auto-resampling -- mic frames arrive at SFU rate (typically 48 kHz), get resampled to STT's expected rate (16 kHz for Silero / Deepgram nova-3); TTS output at 24 kHz gets resampled to 48 kHz for SFU.

Where: livekit-rtc package + voice/io.py + voice/room_io/

Pattern: some of this lives in WebRTC (transport-layer primitive), some in livekit-agents (the Python framework), some in livekit-rtc (the audio I/O bindings). When we self-host, ALL of these come along for free -- they are part of the OSS stack, not Cloud-only features.

What you actually buy with LiveKit (vs just models)

"The model is the easy part. The integration is what separates a usable voice agent from a frustrating one."

Concrete behaviours you experience in the LiveKit Playground -- and where each one actually comes from:

Behaviour you observeComes from
Agent starts speaking ~300 ms after you finish your sentenceFramework -- preemptive_generation (LLM runs speculatively before turn confirmed)
Agent doesn't get interrupted when you say "uh-huh" while it talksFramework -- interruption.backchannel_boundary suppression
Agent stops mid-sentence when you actually do interruptFramework -- interruption detection + TTS cancellation in SpeechHandle scheduler
Agent resumes its sentence when your "interrupt" turned out to be a coughFramework -- resume_false_interruption + false_interruption_timeout
Agent doesn't transcribe its own voice and loop foreverWebRTC client-side AEC + framework aec_warmup_duration window
Agent waits when you pause mid-thought instead of cutting you offModel + framework -- MultilingualModel returns low P(end), framework's endpointing countdown holds turn-end

Agent's voice sounds natural and prosodicModel -- TTS (Cartesia sonic-3). Framework just streams the synthesized frames.

Pattern

Anything about timing, interruption, recovery, coordination between stages = framework.

Anything about acoustic quality, transcript accuracy, generation quality = the model.

The framework wraps the models with a state machine that turns "ML inference results" into "a conversation that feels human."

Where this code actually lives

  • voice/agent_activity.py -- per-turn state machine
  • voice/turn.py -- TurnHandling / Endpointing / Interruption / Preemptive options
  • voice/generation.py -- generate_reply() loop, speculative LLM scheduling
  • voice/speech_handle.py -- per-utterance scheduler with interruption + AEC enforcement
  • voice/audio_recognition.py -- pumps STT events to turn detector, fires endpointing countdown
  • voice/agent_session.py -- AEC warmup timer, user / agent state machines
Strategic implication: we can swap models freely (Sophia's Phase 2 plan rests on this), but rebuilding orchestration would cost 4-8 person-weeks of careful state-machine and timing logic, plus audio I/O plumbing on top. Sticking with LiveKit lets us spend engineering time on model quality and RAG quality, not on rebuilding what already works.

Three-process model (when worker runs)

  [ AgentServer main process ]              ← cli.run_app(server)
    Process pool + WS-to-SFU manager         No ML — pure config
              │ spawns N
              ▼
  [ Worker subprocess #N ]                  ← per user session
    AgentSession orchestrator                prewarm: loads Silero VAD
    Runs Assistant.entrypoint                HTTPS to remote STT/LLM/TTS
              │ IPC for turn detection
              ▼
  [ Inference runner subprocess ]           ← framework auto-spawns
    Loads turn-detector ONNX once            Serves all workers via IPC

Override hooks are how custom plugins integrate. llm_node is where Sophia's AwsRagLLM wires in — intercept chat_ctx, hit AWS RAG endpoint, return ChatChunk stream.

Three-ring tunable model

For each pipeline stage, every knob lives in one of three rings:

  [ Plugin constructor ]      ← model quality (temperature, voice, speed)
                                  per-provider, NOT on Agent
  [ Agent / Session args ]    ← orchestration (instructions, tools, max_tool_steps)
                                  framework-level, provider-agnostic
  [ turn_handling block ]     ← timing & UX (endpointing, interruption, preemption)
StagePlugin knobs (model-specific)Framework knobs (orchestration)turn_handling
STT model, endpointing, keywords, smart_format, diarize, language vad, stt, Agent.stt_node override turn_detection, endpointing.{min,max}_delay
LLM temperature, max_completion_tokens, parallel_tool_calls, reasoning_effort, prompt_cache_key instructions, tools, mcp_servers, chat_ctx, max_tool_steps, llm_node override preemptive_generation.{enabled, max_speech_duration}
TTS voice, speed, emotion, volume, add_timestamps tts_text_transforms, aec_warmup_duration, use_tts_aligned_transcript, transcription_node + tts_node overrides interruption.* (mostly TTS-reaction)
Insight: The interruption.* block is mostly about how TTS reacts to user speech, not about detecting it. VAD/turn-detection produce the signal; interruption args decide what to do with it.
